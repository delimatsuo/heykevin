# What iOS clears when account deletion completes

This inventory covers the local Settings completion. The existing [response parser and completion](../ios/Kevin/Services/AccountDeletion.swift) accept an explicit successful response or an already-deleted response (401 or 404). A failed request keeps the session available for a retry. A reply belonging to an obsolete or consumed operation has no effect.

| State | Current behavior | Ordinary storage or lifetime |
| --- | --- | --- |
| Contractor ID, Kevin number, country, onboarding, API bearer | Success clears these in that order. Settings passes the empty bearer to the API client after the other four assignments. | ID and bearer use Keychain; number, country and onboarding enqueue writes to standard defaults. |
| Call presentation, read/notification state, service binding | Changing the ID invalidates the old presentation lease and its screening snapshot. It resets the current read set, unread count, pending call notification and binding. | Call presentation and binding are in memory. Read IDs have a separate defaults key for each contractor; dropping the current set does not erase that contractor's stored key. |
| Account profile and Apple identity | Completion does not clear owner/business details, service type, mode, the Apple user ID or the transient Apple identity token. | Profile fields are in defaults, Apple user ID is in Keychain, and the identity token is in memory. |
| Subscription status, tier and account UUID | Completion does not clear these cached values. They describe the account; the server remains authoritative. Deleting a Kevin account does not cancel an Apple subscription. | Keychain. |
| Explicit consent to upload contacts | Completion does not reset this account decision. The consent bit is separate from the system's Contacts permission. | Standard defaults. |
| Integration and calling settings | Integration indicators, forwarding activation, carrier selection, contact ringing, tone, reply, interruption and language settings receive no explicit reset here. This inventory does not decide which preferences should follow the device. | Standard defaults for the AppState mirrors. |
| APNs and VoIP device tokens | Kept. These identify the installation for notifications; keeping them locally does not establish a registration for any account. | Device-scoped values in AppState. |

The [completion tests](../ios/KevinTests/AccountDeletionTests.swift) exercise the real fence and reset on a synthetic, in-memory AppState. The observable bearer writer records the requested value and the state when it is written. The call assertions concern ownership of the presentation and transcript, not native call teardown. Three strict expected failures track the signed-out profile/Apple identity, subscription cache, and explicit consent invariants; an unexpected pass calls for reviewing the corresponding test.

## Fresh AppState hydration

The [persistence tests](../ios/KevinTests/AccountDeletionTests.swift) seed a UUID-named Foundation defaults suite and synthetic protected values for account A. They run the same completion, [bearer setter](../ios/Kevin/Services/APIClient.swift), [AppState initializer and active-use refresh](../ios/Kevin/Models/AppState.swift) used by the app. Each fresh instance opens a new defaults handle and uses a new private session epoch, notification center and Keychain manager. Its reader, writer and remover operate on an independently decoded copy of the protected values. The tests take snapshots from the underlying stores before hydration.

| Fixture boundary | Observed local state |
| --- | --- |
| Confirmed deletion after the main queue drains, with no nonempty legacy credentials | The protected ID and bearer are absent. Defaults contain empty number and country strings and false onboarding. A fresh instance enters onboarding with invalid local auth. A’s read-call key remains in the suite, and the signed-out read set is empty. The table above lists the retained profile, Apple ID, subscription cache and consent. Six strict expected failures track business name, Apple ID, subscription status, tier, UUID and consent individually. The carrier preference also survives. |
| Failed deletion or late success from the consumed attempt | Neither store changes. A new deletion attempt can begin, and A hydrates as ready with the original bearer. |
| During confirmed completion, at entry to the bearer setter callback and immediately after the setter returns | Both snapshots still hold A’s number, country and true onboarding. The ID has already been removed. The first snapshot retains the bearer, and the second has removed it. A fresh instance constructed from either snapshot in a separate suite enters recovery. The source instance can finish its queued writes independently. |
| Bearer read denied before the deletion fence checks auth | The reply is rejected, its operation remains pending, and credentials and defaults survive. An available read restores the original auth context for that operation. |
| Bearer read denied inside the setter after the fence accepts the reply | The setter reads an empty old bearer and skips removal. The ID has been removed, the bearer survives, and a fresh unlocked instance enters onboarding. |
| The protected transport accepts reads but silently ignores both removals | Both removals are attempted and A’s stored credentials survive. A fresh instance with unavailable protected reads enters the storage-unavailable gate. Refreshing that instance after unlock enters onboarding. A separate instance initially opened with readable storage hydrates both local credentials while onboarding is false. |
| Legacy ID and bearer in defaults alongside secure credentials | While the secure copies exist, the legacy copies stay in defaults. After secure removal a subsequent migrating read can restore the legacy values. The fixture reaches onboarding with those legacy local credentials. The suite also covers migration when the legacy entries are the only copies. |

In the fixture with empty legacy credential entries, the signed-out state still contains A’s saved Apple ID and consent after deletion. The [existing-account restore coordinator](../ios/Kevin/Services/AccountRestoreCoordinator.swift) receives the actual retained ID, Apple ID and number through its ordinary non-recovery entry point, with a synthetic lookup and profile for existing account B. After restore, a fresh instance hydrates B’s credentials, profile, subscription and read IDs. The coordinator clears A’s consent and integration indicators, makes no contact-sync request, and preserves the carrier preference. A’s old read-call key remains separate from B’s. New-account creation and provisioning use other paths.

A separate synthetic case combines duplicate legacy credentials for B with A’s surviving consent. Ordinary hydration can then supply B as the retained local ID. After a mocked, freshly verified B restore, the coordinator treats matching IDs as evidence that cached consent belongs to B: the consent survives into fresh state and the injected contact-sync counting callback is invoked. Two exact strict expectations track the consent-ownership and no-sync invariants separately. This case uses no contacts or provider calls. It is conditional on the modeled preexisting duplicate store; it does not establish actual migration history, prevalence, provider acceptance or transfer of contacts.

Each checkpoint is a same-process observation of a named defaults domain and a modeled protected store. Queue sentinels distinguish deferred number, country and onboarding writes from synchronous consent and read-call changes. Process termination, power loss, physical Keychain accessibility, server authentication, caller media, provider operations and user-visible disclosure are outside this evidence.
