# What iOS clears when account deletion completes

This inventory covers the local Settings completion. The [response parser and completion](../ios/Kevin/Services/AccountDeletion.swift) accept an explicit successful response (`2xx` with `{"status": "ok"}`) or an already-deleted response (`401` or `404`). A failed request keeps the session available for a retry. A reply belonging to an obsolete or consumed operation has no effect.

When deletion is confirmed, `AccountDeletionFlow.complete` invokes `AppState.resetDeletedAccountState()` and then calls `writeBearer("")` last:

| State | Current behavior | Ordinary storage or lifetime |
| --- | --- | --- |
| Account profile and mode | `resetDeletedAccountState()` resets `userName`, `businessName`, `businessAddress`, `businessCity`, and `serviceType` to `""`, and resets `mode` to `"business"` (`kevinMode`), before `isOnboarded = false` and `writeBearer("")`. | Standard defaults (queued on the main queue for the `AppState` mirrors). |
| Kevin number, country, forwarding, and integrations | Resets `kevinNumber` and `countryCode` to `""`, sets `forwardingActivated = false`, `jobberConnected = false`, and `googleCalendarConnected = false`, and queues removal of `"forwardingActivatedFor"` from defaults. | Standard defaults (queued on the main queue). |
| Apple identity and transient auth/recovery state | Clears `appleIdentityToken`, `needsReauth`, `recoveryCommitPending`, and `pendingAccountRecovery` in memory; deletes `"accountRecoveryCommit"` from Keychain when present (`read != .missing`); and sets `appleUserId = ""`, scrubbing any nonempty legacy `appleUserId` in defaults, clearing migration tracking, and deleting `"appleUserId"` from Keychain. | `appleIdentityToken`, `needsReauth`, `recoveryCommitPending`, and `pendingAccountRecovery` are in memory; `"appleUserId"` and `"accountRecoveryCommit"` use Keychain. |
| Contractor ID, onboarding, and API bearer | Clears `contractorId` (scrubbing any nonempty legacy `contractorId`, clearing migration tracking, deleting `"contractorId"` from Keychain, and advancing the session epoch), later sets `isOnboarded = false` (`sessionState = .notOnboarded`, advancing the session epoch), and finally calls `writeBearer("")` (scrubbing any nonempty legacy `contractorApiToken`, deleting `"contractorApiToken"` from Keychain, and advancing the session epoch). | `contractorId` and `contractorApiToken` use Keychain; `isOnboarded` queues a write to standard defaults. |
| Call presentation, read/notification state, service binding | Synchronously removes `"readCallIds_<deletedId>"` from defaults for the deleted contractor while leaving other accounts' `"readCallIds_<otherId>"` keys untouched. Clearing `contractorId` invalidates the owned presentation lease and its screening snapshot, and resets the in-memory `readCallIds` set, `unreadCallCount`, pending call notification fields, and `serviceBinding`. | Call presentation and binding are in memory; per-contractor read IDs are stored synchronously in standard defaults under `"readCallIds_<id>"`. |
| Subscription status, tier, and account UUID | Resets in-memory `subscriptionStatus` to `"trial"`, `subscriptionTier` to `"none"`, and `subscriptionUUID` to `""` with `didSet` Keychain writes suppressed (`isClearingSubscriptionCache`), and explicitly deletes `"subscriptionStatus"`, `"subscriptionTier"`, and `"subscriptionUUID"` from Keychain. Initial `AppState` hydration likewise suppresses `didSet` Keychain writes (`isHydratingInitialStorage`) so cold launches do not re-save `"trial"` or `"none"`. Deleting a Hey Kevin account still does not cancel an Apple subscription; the server and StoreKit remain authoritative on future sign-in. | Keychain cache (`subscriptionStatus`, `subscriptionTier`, `subscriptionUUID`) backed by server truth. |
| Explicit consent to upload contacts | `resetDeletedAccountState()` revokes `contactsUploadConsent` and removes `contactsUploadConsentOwner` synchronously (also enforced when `contractorId` clears). Automatic and restore contact sync require owned consent matching a non-migrated contractor ID (or a verified new-signup continuation). Separate from iOS Contacts permission. | Standard defaults (`contactsUploadConsent` and `contactsUploadConsentOwner`). |
| Carrier and non-identifying calling preferences | Kept: `isVerizonCarrier`, `ringThroughContacts`, `sitToneEnabled`, `autoReplySms`, `smartInterruption`, and `kevinLanguage`. | Standard defaults for the `AppState` mirrors. |
| APNs and VoIP device tokens | Kept (`pushToken` and `voipToken` in memory). These identify the installation for notifications; keeping them locally does not establish a registration for any account. | Device-scoped values in `AppState`. |

The [completion tests](../ios/KevinTests/AccountDeletionTests.swift) exercise the real fence and `resetDeletedAccountState()` on a synthetic, in-memory `AppState`. A Combine subscriber on `$sessionState` and the observable bearer writer verify that all profile, Apple identity, integration/forwarding, recovery, and subscription properties are already reset when `sessionState` transitions to `.notOnboarded` (while bearer writes are still empty) and remain in place when `writeBearer("")` runs last, across both `"active"` / `"businessPro"` and `"expired"` / `"personal"` starting states. The call assertions verify presentation and transcript ownership invalidation rather than native call teardown.

## Fresh AppState hydration

The [persistence tests](../ios/KevinTests/AccountDeletionTests.swift) seed a UUID-named Foundation defaults suite and synthetic protected values for account A (including `"kevinMode": "personal"` so resetting `mode` to `"business"` is non-vacuous). They run the same completion, [bearer setter](../ios/Kevin/Services/APIClient.swift), and [`AppState` initializer and active-use refresh](../ios/Kevin/Models/AppState.swift) used by the app. Each fresh instance opens a new defaults handle and uses a new private session epoch, notification center, and Keychain manager whose reader, writer, and remover operate on an independently decoded copy of the protected values.

| Fixture boundary | Observed local state |
| --- | --- |
| Confirmed deletion after the main queue drains, with no nonempty legacy credentials | Keychain is empty (`contractorId`, `appleUserId`, `subscriptionStatus`, `subscriptionTier`, `subscriptionUUID`, and `contractorApiToken` removed in that order, with zero Keychain writes during deletion or reopen). Defaults hold cleared profile strings, `"kevinMode": "business"`, empty `kevinNumber` and `countryCode`, `false` `isOnboarded`, `false` `forwardingActivated`, `false` `jobberConnected`, `false` `googleCalendarConnected`, `false` `contactsUploadConsent`, and no `contactsUploadConsentOwner`, `forwardingActivatedFor`, or `readCallIds_account-A` keys, while preserving `readCallIds_account-B`, empty-string legacy suite sentinels, `isVerizonCarrier`, and non-identifying calling preferences. A fresh instance enters `.notOnboarded` with invalid local auth, clean profile and Apple identity, default subscription state (`"trial"`, `"none"`, `""`), revoked consent, and preserved device/calling preferences. |
| Confirmed deletion with a recovery checkpoint marker and `"trial"` / `"none"` subscription cache | Even when Keychain starts with `"subscriptionStatus": "trial"`, `"subscriptionTier": "none"`, `"subscriptionUUID"`, and an `"accountRecoveryCommit"` entry (either an encoded `AccountRecoveryCheckpoint` with `recoveryCommitPending == true` or `"complete"` after a prior recovery), confirmed deletion deletes `"accountRecoveryCommit"` and all three subscription keys without Keychain writes, clears `recoveryCommitPending` and `pendingAccountRecovery`, and a fresh launch enters `.notOnboarded` with empty `contractorId` and `appleUserId` instead of `.needsRecovery`. |
| Failed deletion or late success from the consumed attempt | Neither store changes. A new deletion attempt can begin, and A hydrates as `.ready` with the original bearer and owned consent. |
| During confirmed completion, at entry to the bearer setter callback and immediately after the setter returns | Both snapshots already have `contractorId`, `appleUserId`, `subscriptionStatus`, `subscriptionTier`, and `subscriptionUUID` deleted from Keychain, contact-upload consent revoked, and `readCallIds_account-A` removed synchronously from defaults, while queued defaults (`isOnboarded`, `kevinNumber`, `countryCode`, `businessName`, etc.) flush only after the main queue drains. The first snapshot retains `contractorApiToken` and the second has removed it. A fresh instance constructed from either snapshot in a separate suite enters `.needsRecovery`. |
| Bearer read denied before the deletion fence checks auth | The reply is rejected, its operation remains pending, and credentials and defaults survive. An available read restores the original auth context for that operation. |
| Bearer read denied inside the setter after the fence accepts the reply | Because an unavailable Keychain read is not verified absence, the setter still scrubs any nonempty legacy bearer and attempts Keychain removal across all six account Keychain keys. When the underlying deletes succeed, Keychain is empty and a fresh unlocked instance enters `.notOnboarded` with clean profile, empty `appleUserId`, default subscription state (`"trial"`, `"none"`, `""`), and invalid local auth. |
| The protected transport accepts reads but silently ignores all six removals | All six removals are attempted and A's protected items survive behind the `.notOnboarded` gate (`sessionGeneration == token.auth.generation + 3`). A fresh instance opened while locked enters `.storageUnavailable` with zero Keychain writes; unlocking and refreshing stays `.notOnboarded` with empty `contractorId` and `appleUserId` and default subscription values (`"trial"`, `"none"`, `""`). A separate instance initially opened with readable storage stays `.notOnboarded` (`isOnboarded == false`) with contact-upload consent revoked even though the ignored Keychain items remain readable. |
| Duplicate nonempty legacy ID, bearer, and Apple user ID in defaults alongside secure credentials | Reading with an existing secure Keychain item, refreshing after unlock, or clearing credentials during deletion scrubs nonempty legacy `contractorId`, `contractorApiToken`, and `appleUserId` duplicates from defaults (including duplicates injected immediately before deletion) while leaving empty-string suite sentinels intact. Confirmed deletion leaves neither secure nor legacy credentials or `appleUserId` to repopulate on the next launch. |

In the fixture with empty legacy credential entries, the signed-out state after A's deletion has empty `contractorId`, `appleUserId`, `kevinNumber`, profile, integration indicators, and subscription cache, removed `readCallIds_account-A`, and revoked contact-upload consent, while `readCallIds_account-B` and `isVerizonCarrier` survive. The [existing-account restore coordinator](../ios/Kevin/Services/AccountRestoreCoordinator.swift) receives those empty retained fields through its non-recovery entry point, restores existing account B from a synthetic lookup and profile, and hydrates B's credentials, profile, subscription, and `readCallIds_account-B` while keeping `readCallIds_account-A` absent, keeping B's consent `false`, making no contact-sync request, and preserving `isVerizonCarrier`. New-account creation and provisioning use other paths.

Both post-fix deletion and historical pre-fix deleted stores with migrated legacy credentials reject unowned or mismatched consent. Even if a historical store lacks Keychain credentials and migrates B's legacy ID into `AppState` on launch, `AccountPersistence` records that the ID came from legacy defaults rather than an authenticated Keychain session, so `reconcilePersistedConsent` revokes bare, A-owned, or stale B-owned consent before restore. Restoring B with a matching retained contractor ID therefore keeps consent `false` and invokes no contact-sync callback. Locked cold launches hold in-memory consent `false` without mutating defaults until unlock reconciles secure storage, and same-account recovery preserves owned consent.

Remaining boundaries stay explicit: device tokens (`pushToken`, `voipToken` in memory), `isVerizonCarrier`, non-identifying calling preferences (`ringThroughContacts`, `sitToneEnabled`, `autoReplySms`, `smartInterruption`, `kevinLanguage`), and other accounts' `readCallIds_<otherId>` keys intentionally survive confirmed deletion; a Keychain transport that silently ignores deletes still leaves protected items behind the `.notOnboarded` gate; true account-switch media policy remains unresolved outside these deletion/restore flows; and each persistence checkpoint is a same-process observation of an isolated defaults domain and modeled protected store rather than OS process-termination, power-loss, hardware Keychain accessibility, live server authentication, caller media, or live provider qualification.
