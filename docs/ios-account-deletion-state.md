# What iOS clears when account deletion completes

This inventory covers the local Settings completion. The existing [response parser and completion](../ios/Kevin/Services/AccountDeletion.swift) accept an explicit successful response or an already-deleted response (401 or 404). A failed request keeps the session available for a retry. A reply belonging to an obsolete or consumed operation has no effect.

| State | Current behavior | Ordinary storage or lifetime |
| --- | --- | --- |
| Contractor ID, Kevin number, country, onboarding, API bearer | Success clears these in that order. Settings passes the empty bearer to the API client after the other four assignments. | ID and bearer use Keychain; number, country and onboarding enqueue writes to standard defaults. |
| Call presentation, read/notification state, service binding | Changing the ID invalidates the old presentation lease and its screening snapshot. It resets the current read set, unread count, pending call notification and binding. | Call presentation and binding are in memory. Read IDs have a separate defaults key for each contractor; dropping the current set does not erase that contractor's stored key. |
| Account profile and Apple identity | Completion does not clear owner/business details, service type, mode, the Apple user ID or the transient Apple identity token. | Profile fields are in defaults, Apple user ID is in Keychain, and the identity token is in memory. |
| Subscription status, tier and account UUID | Completion does not clear these cached values. They describe the account; the server remains authoritative. Deleting a Kevin account does not cancel an Apple subscription. | Keychain. |
| Explicit consent to upload contacts | Changing the contractor ID to empty revokes `contactsUploadConsent` and removes `contactsUploadConsentOwner`. Automatic and restore contact sync require owned consent matching a non-migrated contractor ID (or a verified new-signup continuation). The consent decision remains separate from the system's Contacts permission. | Standard defaults (`contactsUploadConsent` and `contactsUploadConsentOwner`). |
| Integration and calling settings | Integration indicators, forwarding activation, carrier selection, contact ringing, tone, reply, interruption and language settings receive no explicit reset here. This inventory does not decide which preferences should follow the device. | Standard defaults for the AppState mirrors. |
| APNs and VoIP device tokens | Kept. These identify the installation for notifications; keeping them locally does not establish a registration for any account. | Device-scoped values in AppState. |

The [completion tests](../ios/KevinTests/AccountDeletionTests.swift) exercise the real fence and reset on a synthetic, in-memory AppState. The observable bearer writer records the requested value and the state when it is written. The call assertions concern ownership of the presentation and transcript, not native call teardown. Two strict expected failures track the signed-out profile/Apple identity and subscription cache invariants; an unexpected pass calls for reviewing the corresponding test.

## Fresh AppState hydration

The [persistence tests](../ios/KevinTests/AccountDeletionTests.swift) seed a UUID-named Foundation defaults suite and synthetic protected values for account A. They run the same completion, [bearer setter](../ios/Kevin/Services/APIClient.swift), [AppState initializer and active-use refresh](../ios/Kevin/Models/AppState.swift) used by the app. Each fresh instance opens a new defaults handle and uses a new private session epoch, notification center and Keychain manager. Its reader, writer and remover operate on an independently decoded copy of the protected values. The tests take snapshots from the underlying stores before hydration.

| Fixture boundary | Observed local state |
| --- | --- |
| Confirmed deletion after the main queue drains, with no nonempty legacy credentials | The protected ID and bearer are absent. Defaults contain empty number and country strings, false onboarding, false contact-upload consent, and no consent-owner key. A fresh instance enters onboarding with invalid local auth and revoked consent. A’s read-call key remains in the suite, and the signed-out read set is empty. The table above lists the retained profile, Apple ID, and subscription cache. Five strict expected failures track business name, Apple ID, subscription status, tier and UUID individually. The carrier preference also survives. |
| Failed deletion or late success from the consumed attempt | Neither store changes. A new deletion attempt can begin, and A hydrates as ready with the original bearer and owned consent. |
| During confirmed completion, at entry to the bearer setter callback and immediately after the setter returns | Both snapshots still hold A’s number, country and true onboarding, while contact-upload consent has already been revoked synchronously with the ID clear. The ID has already been removed. The first snapshot retains the bearer, and the second has removed it. A fresh instance constructed from either snapshot in a separate suite enters recovery. The source instance can finish its queued writes independently. |
| Bearer read denied before the deletion fence checks auth | The reply is rejected, its operation remains pending, and credentials and defaults survive. An available read restores the original auth context for that operation. |
| Bearer read denied inside the setter after the fence accepts the reply | Because an unavailable Keychain read is not verified absence, the setter still scrubs any nonempty legacy bearer and attempts Keychain removal. When the underlying delete succeeds, both the ID and bearer are absent and a fresh unlocked instance enters onboarding with invalid local auth. |
| The protected transport accepts reads but silently ignores both removals | Both removals are attempted and A’s stored credentials survive behind the signed-out gate. A fresh instance with unavailable protected reads enters the storage-unavailable gate. Refreshing that instance after unlock enters onboarding without hydrating the contractor ID. A separate instance initially opened with readable storage hydrates both local credentials while onboarding is false, with contact-upload consent revoked. |
| Duplicate nonempty legacy ID and bearer in defaults alongside secure credentials | Reading with an existing secure Keychain item, refreshing after unlock, or writing/clearing credentials scrubs nonempty legacy duplicates from defaults while leaving empty-string suite sentinels intact. Confirmed deletion therefore leaves neither secure nor legacy credentials to repopulate on the next launch. |

In the fixture with empty legacy credential entries, the signed-out state retains A’s saved Apple ID while A’s contact-upload consent has been cleared. The [existing-account restore coordinator](../ios/Kevin/Services/AccountRestoreCoordinator.swift) receives the actual retained ID, Apple ID and number through its ordinary non-recovery entry point, with a synthetic lookup and profile for existing account B. After restore, a fresh instance hydrates B’s credentials, profile, subscription and read IDs. The coordinator clears A’s integration indicators, keeps B’s consent false, makes no contact-sync request, and preserves the carrier preference. A’s old read-call key remains separate from B’s. New-account creation and provisioning use other paths.

Both post-fix deletion and historical pre-fix deleted stores with migrated legacy credentials reject unowned or mismatched consent. Even if a historical store lacks Keychain credentials and migrates B’s legacy ID into `AppState` on launch, `AccountPersistence` records that the ID came from legacy defaults rather than an authenticated Keychain session, so `reconcilePersistedConsent` revokes bare, A-owned, or stale B-owned consent before restore. Restoring B with a matching retained contractor ID therefore keeps consent false and invokes no contact-sync callback. Locked cold launches hold in-memory consent false without mutating defaults until unlock reconciles secure storage, and same-account recovery preserves owned consent.

Remaining gaps stay explicit: confirmed deletion still retains cached profile fields, `appleUserId`, and cached subscription metadata (tracked by the two completion and five durable strict expected failures); a Keychain transport that silently ignores deletes still leaves credentials behind the signed-out gate; true account-switch media policy remains unresolved outside these deletion/restore flows; and each checkpoint is a same-process observation of a named defaults domain and a modeled protected store rather than OS process-termination, power-loss, hardware Keychain accessibility, live server authentication, caller media, or live provider evidence.
