> After secure storage is usable, detect an onboarded installation with incomplete credentials and present **existing-account recovery**. Distinguish missing items from temporary storage unavailability.

## Pinned implementation contract

1. Add typed Keychain reads: a value, confirmed missing item, or unavailable/error status. Only `errSecItemNotFound` is missing; malformed data is an error. Keep `AfterFirstUnlockThisDeviceOnly`. Legacy defaults migration may happen only after a confirmed missing read; remove the legacy value only after a successful Keychain write. Do not overwrite or delete anything on an unavailable read.
2. Add an observable account-session gate in `AppState`, evaluated on active secure-storage refresh. Onboarded + both nonempty credentials becomes ready; either confirmed missing/empty credential requires existing-account recovery; any unresolved storage error stays unavailable and retries on activation. The initial unchecked state must not display a misleading trial/main screen. Do not reset onboarding, the Kevin number, or credentials merely to show recovery. Offer an explicit retry for temporary storage unavailability. Provide injection seams that test these real transitions without real Keychain or persisted owner data.
3. Route the app to an existing-account-only sign-in presentation when recovery is required. Reuse `OnboardingView` with an explicit recovery mode. Explain that signing in reconnects the existing number; no create, phone-entry, purchase, delete-account, or provision fallback is reachable in recovery mode. Existing Session Expired → Sign In Again must enter this recovery mode while retaining identity. Missing local auth in Calls must produce an explicit recovery action/state, while continuing to hide all unowned history and obey epoch/revision guards.
4. Share a testable existing-account restore coordinator with normal returning-user onboarding. Verify the newly supplied Apple identity through lookup; remove the cached-contractor shortcut that can restore a different identity. Stage the returned contractor ID/token and fetch its profile with that explicit token before publishing a session. Reject empty tokens, malformed lookup/profile, inactive accounts, contractor mismatch, or missing server subscription state. In recovery, require a match to any retained contractor ID, Apple identity and Kevin number and require the server number to exist. No fallback to creating/provisioning when lookup or profile fails. Normal new-user setup may proceed to phone entry only after an explicit authenticated not-found result. Preserve incomplete, known existing-account provisioning for ordinary onboarding only.
5. Make lookup outcomes unambiguous: HTTP 401 is Apple authentication failure; HTTP 404 is not found; HTTP 200 with valid nonempty contractor ID/token is found; every other HTTP, transport, or malformed result is a failure. For compatibility with the currently deployed backend, accept only its exact legacy JSON array `[{"error":"Not found"},404]` as not found. Do not infer absence from arbitrary JSON. Scope this repair to the iOS parser; no unrelated lookup/backend migration is needed.
6. Fence asynchronous restore by a per-attempt revision plus captured account/epoch/recovery context. Disable duplicate sign-in submissions while busy. Recheck before and after every await and before publishing. Persist and verify credentials successfully before considering the session ready; a failed save must keep a visible recovery error. Do not reuse a previously cached Apple identity token when the new authorization lacks one. Do not log credentials. Preserve server-authoritative subscription hydration before main UI/paywall routing. Retry must be safe after backend token rotation or partial local persistence. Fully hydrate or clear account-scoped caches; preserve existing contact-upload consent only when a surviving trusted contractor ID matches. A cached number is a continuity check, never authentication evidence. Clear stale read/navigation/registration state at session changes. Reconcile storage on protected-data availability as well as scene activation.
7. Add one serial main-actor notification-registration coordinator with injected status/prompt/APNs-registration/network/current-auth/token dependencies for tests. Account-ready completion (including signing in while already active), foreground activation, and either token callback must use it. Permission status is obtained independently of backend auth. An onboarded ready session with `.notDetermined` requests authorization; `.authorized`/`.provisional` requests APNs registration; `.denied` does not re-prompt. Available ordinary/VoIP tokens are submitted immediately after credentials become ready, without depending on another foreground transition. Keep tokens received before sign-in for that completion. Coalesce concurrent submissions; if a token/auth snapshot changes while in flight, process the newest snapshot. Failed attempts remain retryable on the next callback/foreground/completion; no tight loop. Do not throttle failures as successes.
8. A registration request captures immutable current account ID/token/generation and current ordinary/VoIP tokens. `APIClient.registerDevice` must return explicit success only for HTTP 200 and JSON status `ok`. The coordinator may set registration success only while auth/generation and token snapshot still match. Never overwrite newer callback tokens with old response values. A new auth epoch or changed token invalidates previous registration success. Preserve independent callbacks and partial-token backend merge; do not clear an omitted token or introduce multi-device storage.
9. Move the Settings OS-permission refresh ahead of both auth and network/coalescing guards, preserving fixture isolation and ensuring foreground/tab changes refresh it. Add meaningful sequencing coverage using the production loading seam, not only a helper whose result is unused by the view.
10. Backend `/api/register-device`: missing contractor ID or both tokens empty returns HTTP 400; auth errors retain current HTTP 401/403 and access enforcement; persistence/update failure returns HTTP 500; successful token write and required profile updates return `{status:ok}`. Keep partial token merges, timezone/language update and stale deletion-signal clearing. Avoid logging exception payloads that can contain raw device tokens. Cover actual HTTP status through a router/client with synthetic dependencies; both token arrival orders, saved token replacement, empty input, failed write/update and unauthorized ownership.
